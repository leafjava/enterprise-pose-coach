## 一、我会当场问的 8 个杀手级问题

### Q1｜「你首页那张混淆矩阵，是哪个模型的？」

**问题原文**：「你首页 REAL ENGINE 那一屏，图注写的是『ST-GCN 验证集混淆矩阵 · 11 类动作逐格可核对』。我放大看了，行标签是『八段锦0』到『八段锦7』、『五禽戏0』到『五禽戏5』——15 类，对角线基本全是 1.00。这张图和你说的 MM-Fit 11 类、8898 窗口、93.15%，是同一件事吗？」

**我为什么问**：这是唯一一个能一击定生死的问题。我在验证的不是技术，是**你们对自己数字的口径纪律**。而且你们自己写的路演纪律第 2 条就是「不展示与当前 11 类口径不一致的旧混淆矩阵」——你们违反了自己的规矩。

**答不上来我怎么扣分**：这不是扣分，是清零。一个自称「可审计、可复核、给 HR 做录用参考」的产品，在落地页上把 A 模型的结果标成 B 模型的结果，我会默认后面每个数字都要重新验证，并当场停止听技术部分。

**应该怎么答**：路演前就换掉或删掉。被问到就主动承认血统：「这是历史遗留资产的错误引用，我们的前身是一个八段锦／五禽戏 15 类分类项目，`model/best_model_7_exchange_val_and_test.pth` 就是那份权重、现在仍是默认加载的主模型。我们已经替换。」主动承认比被戳穿好一百倍。

### Q2｜「训练 + 沉淀 + 复用，代码在哪一行？」

**问题原文**：「你整个叙事的核心是『首次调用训练并沉淀 Best 权重，后续调用直接加载』。请现在打开仓库，指给我看：接收训练请求的 HTTP handler 在哪一行？Best 权重的版本注册表在哪？『新权重优于旧权重才升级、旧版可回滚』的比较逻辑在哪？」

**我为什么问**：验证核心创新是代码还是 PPT。我查过了——`web_app.py` 没有 `/api/skill/init`、`/api/skill/best_weights`、`/api/skill/retrain`。`best_weight_id`、`tenant_id`、`decision`、`review_status`、`audit` 在 `web_app.py` 和整个 `src/` 里出现次数是 **0**；它们只存在于 examples 的 JSON、首页营销文案和路演稿生成脚本里。`docs/architecture.md` 列的 `skill_contracts.py`、`posture_standards.py`、`audit.py`、`clawhive_adapter.py` 四个文件全都不存在。唯一的训练代码是个离线 CLI，`src/train.py:117` 就一句 `if val_acc >= best_val_acc: torch.save(...)`——**直接覆盖单一路径，没有租户命名空间、没有版本表、没有和已沉淀权重比较、没有回滚**。`model/` 下也没有任何 `bw_<tenant>_*.pth`。

**扣分**：创新性从 8 掉到 4。你的差异化如果不是代码，你和「写了一份很好的 SKILL.md」的队伍就没区别，而后者不需要 GPU。

**应该怎么答**：**唯一过关的答法是路演前把它做出来。** 一个 `POST /api/skill/init`（收 tenant_id + 数据路径 + 超参 → 调 `run_bounded_training` → 按 `bw_<tenant>_<date>_v<n>.pth` 落盘 → 写 JSON 注册表）+ 一个 `GET /api/skill/best_weights` + 升级门槛（新 val_acc 不优于当前就不升级，旧文件保留）。约 150 行，一晚上能写完。然后**在台上用 curl 演示两次调用**。做不到就诚实降级：「训练链路目前是 CLI，Skill 化是下一步」——README 里其实就是这么写的，别在台上说成已实现。

### Q3｜「我给你 10 万条工厂脱敏样本，你的计数准确率会提升吗？」

**我为什么问**：这是**最致命的技术结构问题**。计数在 `src/live_coach.py:425 _update_rep_count`，只依赖 `_phase_for` 返回的几何阶段；纠错是硬编码角度阈值。**ST-GCN 权重只在 `mode=="auto"` 分支被调用，作用是判断「这个人在做哪个动作」，既不参与计数，也不参与纠错。** 你训练出的 Best 权重再好，深蹲计数准确率一点都不会变。而首页流程图写的是「关键点 → Best 权重推理 → 计数 → 实时纠正」——这条链在代码里不存在。

**扣分**：这一条被问穿，「能力随训练成长」的整个飞轮就塌了，商业价值和创新性一起扣。

**应该怎么答**：两条路，选一条，别含糊。
- **A（诚实收窄，推荐）**：「模型负责识别动作类别，计数和纠错走版本化几何规则。所以我们沉淀的资产是**两件**：动作分类 Best 权重，以及 `config/posture_standards/*.json` 里的阈值与阶段模板。企业数据首先提升的是后者。深蹲计数的模型化是 roadmap 下一步。」这个答法我接受，而且比吹牛更有说服力。
- **B（真做）**：把有效次数判定改成模型输出的一部分。48 小时内不现实，路演前别承诺。

### Q4｜「93.15% 是怎么算出来的？划分是按人分的吗？」

**我为什么问**：`src/train.py:73` 是 `train_test_split(data, labels, test_size=0.1, random_state=118, stratify=...)`——**对滑窗做随机划分**。MM-Fit 21 名受试者的连续动作按 stride=48 切窗，同一个人同一组动作的相邻窗口会同时落进训练集和验证集，这是教科书级泄漏。第 5 轮 Val 93.15% > Train 89.46% 正是泄漏的典型指纹。更糟的是 `train.py:117` 的 best 是**按 val_acc 选的**、没有独立测试集，所以 93.15% 是「选模指标」而非「泛化估计」，双重高估。顺带：`model/VAL_confusion_matrix.png` 和 `model/model7Test_confusion_matrix.png` 的 md5 完全相同——验证集就是测试集，和权重文件名 `best_model_7_exchange_val_and_test.pth` 说的是同一件事。

**扣分**：技术尽调这一维直接判定不合格。招聘筛选是影响候选人机会的高风险决策，你连自己的评估口径都没绷住，我不可能相信你在客户现场的误拒率。

**应该怎么答**：「按窗口随机划分，不是按人划分，所以 93.15% 高估了泛化能力。路演前我们重跑了 **leave-subjects-out**（17 人训练 / 4 人验证），数字是 XX%。这个更低的数字才是我们对外的口径。」——**去把这个数跑出来。5 轮 CPU 训练很快。哪怕掉到 70%，一个 70% 的诚实数字在我这里的分数远高于 93.15% 的漂亮数字。** 而且它正好证明了你的核心论点：通用数据不够用，必须用企业数据训练。**你的弱点恰好是你的商业逻辑。**

### Q5｜「工厂招聘真的会考深蹲 50 次吗？你访谈过几个招聘负责人？」

**我为什么问**：我做过制造业 HR SaaS。一线工厂招聘的体检环节我熟，深蹲 50 次不是普遍项目。而 `docs/tasks.md` 里 T-034「访谈 5 名招聘负责人」是 `todo`，T-035 ROI 模板 `todo`，`docs/PRD.md` 自己写着「定价必须在得到首批访谈和人工成本基线后确定」。**零客户访谈、零定价、零成本基线。** 而作为标准依据的 `config/posture_standards/recruit_squat_50_v1.json`，`source.kind` 是 `project_owned_engineering_template`、description 是 "Synthetic front-view template derived from the existing squat phase and geometry rules"、`production_review_required: true`——连这个「企业招聘标准」本身都是你们从自己代码反推的合成模板，没有任何 HR 或 EHS 专家背书。

**扣分**：商业价值从 8 掉到 5。「50 次深蹲」如果是自己拍的，第一页痛点就是虚构的，后面所有 ROI 都是空转。

**应该怎么答**：**别硬撑说访谈过。**「深蹲 50 次是我们的可运行 Demo 标准，不是我们宣称的行业惯例。真正普遍存在的是**转岗与在岗的动作 SOP 考核和安全搬运复训**——那里有 EHS 预算、有强制复训周期、有工伤成本。招聘筛选是我们最容易演示的场景，在岗训练是我们真正要卖的场景。我们下一步做的第一件事是访谈 5 家制造企业的 EHS 负责人，而不是继续加动作。」这个重排能救回商业价值分，而且和你们 PRD 里「第二阶段」的判断一致，只是你们把顺序讲反了。

### Q6｜「你的达标认证，我能不能自己给自己发一张？」

**我为什么问**：`web_app.py:632 create_certification` —— 没有鉴权、没有 tenant、没有 Idempotency-Key、**不校验 session_id、不查会话存储**，完全信任客户端传来的 `rep_count`。任何人 `curl -d '{"name":"张三","worker_id":"1","exercise":"squats","rep_count":50}'` 就能拿到证书。你整个产品的价值主张是「可解释、可复核、可回写招聘台账的证据」，而**证据本身和检测过程没有任何数据绑定**。附带：`data/certifications.json` 现在躺着两条记录，姓名 `leaf`，工号 `1001` 和 `666`——README 写着「Demo 一律使用虚构身份」。

**扣分**：可复用稳定性扣到 3 分以下。这不是「待接线」，这是核心资产没有完整性保护。

**应该怎么答**：路演前改成必须携带 `session_id`、服务端从会话读次数、不接受客户端传值。**约 20 行，今晚就改。** 改完台上多一句话可以说：「我们的证书不是页面上的一个数字，是从服务端会话里派生出来的。」

## 二、这个路演最大的 5 个风险

### 风险 1｜首页的「真实性证据」区块本身是错的——一张图能毁掉整场

`templates/home.html:315` 的图注写「11 类动作逐格可核对」，实际图片是 15 类八段锦／五禽戏，对角线 0.96–1.00，区块标题是「真模型、真推理、真数据」。而路演大纲第 01、03 页都用首页实机截图。

**补救（今晚 30 分钟）**：重新生成 11 类矩阵替换，或直接删掉这一屏。同时全仓库搜「11 类」，确认没有别的图文错配。

### 风险 2｜核心叙事「训练 + 沉淀 + 复用」在代码里是零

无 `/api/skill/*` 路由；`best_weight_id`／`tenant_id`／`decision`／`audit` 在运行时代码中出现 0 次；`architecture.md` 承认四个模块「仅设计」；`train.py:117` 只是覆盖单文件；`model/` 下无任何 `bw_*`；`skill-build/enterprise-pose-coach.zip` 在 README 里标「已实现」但磁盘上不存在；`docs/tasks.md` 中 T-020～T-028 九项全 `todo`，包括 T-023「确认官方 Skill 包规范」——**说明你们连 ClawHive 的 Skill 真实规范都还没拿到**。

**最刺眼的一处**：你们自己的 `references/api-mapping.md` 写着「现有 Flask API 只要求动作和图像帧，**没有**租户、批次、标准版本、幂等键、复核状态等企业级字段」，整张映射表右列全是「新增」。你们知道，但首页和 SKILL.md 的语气像是已经上线了。

**补救**：(1) 今晚写 `/api/skill/init` + 注册表 + 升级门槛，台上用 curl 演示两次调用；(2) 做不完就把所有现在时改成「设计契约／下一步」，并在路演里主动说是最后接线项。

### 风险 3｜模型不在决策链路上——飞轮没有传动轴

`_update_rep_count` 只看几何阶段；`_squat_errors` 是硬编码角度阈值；ST-GCN 仅做动作分类。首页流程图「Best 权重推理 → 计数 → 实时纠正」在代码中不存在。

**附带一个具体 bug**：`_update_rep_count` 开头对非专项动作直接 return，而 `situps`／`jumping_jacks`／`tricep_extensions`／`lateral_shoulder_raises` 的 `_phase_for` 永远返回 `ready`。**这四个动作的计数永远是 0。** 但 SKILL.md §3 明确把 `situps` 列为输入动作。如果评委说「演示一下仰卧起坐」，你会返回 0 次 → 在你们的决策矩阵里就是 `not_met`——**一个真实候选人会因此被误判为体能不达标**。

**补救**：(a) 路演绝口不提那 5 个通用动作可计数，Demo 只用深蹲；(b) 非专项动作 `rep_count` 返回 `null` 并标注「暂不支持计数」；(c) 叙事上把「沉淀的资产」从「权重」扩为「**权重 + 版本化姿态标准**」。

### 风险 4｜93.15% 的口径 + 演示机从未验收

窗口级随机划分、无独立测试集、best 按 val 选、Val > Train、VAL 与 Test 混淆矩阵 md5 相同、权重名叫 `exchange_val_and_test`。`docs/real-evidence.md` 第四节的 RTX 5070 Ti「GPU 推理记录」其实是 **Flask 启动日志**，而训练命令是 `--device cpu --epochs 5`。演示机侧 AC-08、T-029、T-030 全 `todo`。

**补救**：跑 leave-subjects-out；别把 GPU 启动日志说成训练日志；**演示机至少 3 次冷启动彩排 + 一次断网**；准备录屏作为主 Demo。

### 风险 5｜商业假设零验证 + 认证记录无完整性

T-034、T-035 `todo`，PRD 承认无定价；招聘标准是自产合成模板；认证接口无鉴权不绑定 session；`certifications.json` 里是开发者本人的记录；`web_app.py:251 estimate_heart_rate` 用像素位移编造心率（`base_hr = 70 + min(avg_movement*500, 50)`），并在 `web_app.py:279` 以「心率: X BPM」喂给 LLM 生成「心率评估」——**一个用于 HR 决策的产品里出现伪造生理指标，是合规炸弹**。

**补救**：认证接口从 session 取次数；清空并替换 certifications.json；**把心率功能和所有心率文案从 Demo 路径下线**；台上把「零访谈」翻译成 ask。
