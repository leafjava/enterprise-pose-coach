# 练了么 · 5 分钟 Demo 视频脚本：实时监测 + 实时纠正的垂直基座 Skill

参考：仓库根目录 [README.md](../README.md)、[PRD](PRD.md)、[tasks](tasks.md)、[real-evidence](real-evidence.md)、[acceptance](acceptance.md)。Demo 种子数据 [enterprise_demo.json](../data/demo/enterprise_demo.json)。

这版脚本用于正式录屏和现场路演：主线不是"演示一个固定推理的 AI App"，而是展示**练了么本身就是一个垂直领域基座训练 Skill**。当 ClawHive Agent 调用我们的 Skill 时，它会选取企业岗位相关数据集，自动搜寻开源数据集，按这套设计训练专属的垂直基座模型——在通用基座之上做"基座 + 基座"的深度垂直扩展；训练好的垂直基座之上，再叠加**实时监测 + 实时纠错**的应用层，让企业拥有"自己的动作识别引擎"。

一句话主线：

> 练了么不是"调用固定 API 的传统 Skill"，而是一个**自带基座训练能力的垂直 Skill**：Agent 接入后选取数据集 → 自动训练专属基座 → 在该基座上做实时监测 + 实时纠错。亮点是"实时"两个字——监测是实时的、纠错是实时的、反馈也是实时的。

推荐时长：6–7 分钟。  
推荐展示方式：现场稳定时优先展示 Flask live path（真实摄像头 + 真实垂直基座）；`npm run demo` / `/coach` 作为 100% 稳定的兜底。  
推荐叙事重点：这既不是健身 App，也不是医疗诊断，更不是为了炫技的"动作识别准确率"；它是面向招聘、转岗与在岗训练的 **AI 体能数字员工**，由 ClawHive Agent 调用、按企业岗位数据**现场训练**的垂直基座来驱动。

建议口播：

很多评委看到 ClawHive Skill 的时候，会以为是一个写好的 Markdown 文件 + 几个 API。这是一个常见误解，也是我们想强调的第一件事：

**练了么的 Skill 不是传统 Skill**。

传统 Skill 是固定推理 + 固定 API：Agent 调一下，我返回结果，结束。Markdown 描述长什么样、能力就是什么样，没有"成长"。

练了么的 Skill 是一个**基座训练 Skill**。当 ClawHive Agent 调用我们的 Skill 时，它会：

```text
1. 接收企业岗位相关数据集（或我们代理搜索的开源数据集）
2. 选择与该岗位匹配的微调起点（ST-GCN / RTMPose / 其它基座）
3. 按"基座 + 基座"的设计，在通用基座之上微调出该企业的专属垂直基座
4. 把这个垂直基座 + 实时监测/纠错应用层一起交付给企业
```

这就是"**基座 + 基座**"的含义：一个通用基座（RTMPose/ST-GCN），加上一个企业专属垂直基座（针对该企业岗位、该企业标准、该企业员工微调出来的那一层）。后面跑出来的实时监测 + 实时纠错，都是在这个垂直基座上跑出来的——不是通用模型，是"你的模型"。

评审打点：

- 差异化：不是固定推理服务，是基座训练 Skill。
- 深度：通用基座 + 垂直企业基座的双层架构。
- 可成长：每服务一家企业，就多一个专属垂直基座资产。

## 4. 实时监测 + 实时纠正主 Demo：招聘深蹲 50 次（2:30–4:00）

网页上展示什么：

切到 `/certification`。按顺序展示：

1. 候选人信息录入：姓名 `演示候选人`、工号 `C042`、动作 `深蹲`。
2. 点击"打开摄像头"：浏览器弹权限框，选允许；右上角徽标从 `摄像头未开启` 变为 `摄像头已开启`。
3. 站到画面中间，徽标变成 `手动模式 - 深蹲`，阶段显示 `准备`——实时监测开始。
4. 点击"开始训练"，进入实时识别循环，每一帧画面都被送往垂直基座推理。
5. 候选人在摄像头前完成 1 次完整深蹲（下降 → 底部 → 上升 → 站立），次数从 0 跳到 1，阶段在 `准备 / 下降 / 底部 / 上升` 之间实时切换——这就是"实时监测"。
6. 在底部故意屈膝不足、膝盖内扣或躯干前倾，主提示**立刻**切换为 `再蹲深一点` / `膝盖与脚尖同向` / `保持胸椎中立`，同时听到 Web Speech API 语音播报——这就是"实时纠正"。
7. 因为底部不到位，本次周期不算数；继续做几次完整周期，次数逐次 +1。
8. 连续完成 50 次后点击"结束训练"，弹出结构化总结：次数 50、Top 错误、下一重点。
9. 写入认证记录，自动生成 Canvas PNG 证书 `DEMO-CERT-001`，`data/certifications.json` 多一条脱敏记录。

如果现场没有摄像头或 GPU，用 `npm run dev` + `npm run demo`：先用 `/coach` 演示真实页面、API 和垂直基座推理，再用 `npm run demo` 跑端到端 smoke，输出 `status: passed` 证明 50 次实时计数闭环可复现。

建议口播：

现在进入 Sample 1：招聘深蹲 50 次实时监测 + 实时纠正。这是当前最强、最真实的闭环。

候选人打开 `/certification`，录入虚构信息。打开摄像头后，每一帧画面都会被送到企业专属的垂直基座上推理。RTMPose 抽关键点，48 帧序列喂给 ST-GCN，规则引擎判断这一帧处于哪个阶段、动作是否到位。

"实时"在这里体���在三个层面：

- **实时监测**：阶段徽标在毫秒级内切换 `准备 → 下降 → 底部 → 上升`，每帧都在评估；
- **实时纠正**：在底部故意不到位，主提示立刻变成"再蹲深一点"，Web Speech API 同步播报；
- **实时计数**：必须经过"准备 → 下降 → 底部 → 上升 → 准备"完整周期，计数才 +1；不到位只记错误、不计数。

这就是为什么"实时"是亮点：不是事后总结报告，是当下立刻的反馈。50 次完成后，系统把这次的"动作、次数、Top 错误、规则版本、垂直基座版本、达到状态"写进结构化认证记录，并生成一张 PNG 证书。整个过程没有人手动数，但每个被算的次数都可以被解释。

评审打点：

- 业务闭环：替代考官逐人计数。
- 亮点可视：监测/纠正/计数三层"实时"在画面上同时可见。
- 可解释：每个计数都对应一次完整动作周期。

## 6. ClawHive 编排：基座训练 Skill + 实时纠错 Skill（4:50–5:30）

网页上展示什么：

回到首页，停在"大赛定位：AI-开发主赛道"章节。镜头扫过 ClawHive 五层能力对照表，重点强调"模型层：基座训练 + 实时推理"和"资产层：垂直基座 + 实时纠错 Skill"两行。

随后展示 README 中的"建议输入契约"和"建议输出契约"两段 JSON，以及 `skill-build/enterprise-pose-coach/SKILL.md` 的 §4 "输出契约"表格。

最后切到终端 A，停留几秒让评委看清后端跑的是同一个 Flask 进程，ClawHive 接入只是再套一层编排。

建议口播：

这是 ClawHive 与本项目的结合方式，也是"基座 + 基座"在企业流程中的落地形态。

ClawHive Agent 调用我们的 Skill 时，会分两步走：

```text
Step 1：基座训练 Skill
  Agent 读取企业标准 RECRUIT_SQUAT_50_V1
  → 调用基座训练 Skill，传入企业脱敏样本
  → 产出该企业的垂直基座权重 + 元数据
  → 部署到企业私有推理环境

Step 2：实时纠错 Skill
  HR 在飞书发起"今天 A 批候选人创建深蹲 50 次检测"
  → Agent 调用实时纠错 Skill（绑定该企业的垂直基座）
  → 候选人摄像头前完成动作，实时监测 + 实时纠错
  → 汇总 pass / not_met / inconclusive
  → 把需复核项通知 HR，授权确认后回写招聘台账
```

所以我们的 Skill 在 ClawHive 市场里实际上是**一对**：一个训练 Skill + 一个实时纠错 Skill。训练 Skill 输出垂直基座，纠错 Skill 在垂直基座上做实时反馈。这是"基座 + 基座"在 ClawHive 编排层的直接对应。

`decision` 只允许 `pass`、`not_met`、`needs_retraining` 或 `inconclusive`：技术失败、模型超时、关键点无效必须返回 `inconclusive` 或进入人工复核，不能伪造成 `not_met`。

评审打点：

- 平台契合：直接对齐网易智企 ClawHive 五层能力。
- 双 Skill 架构：训练 Skill + 实时纠错 Skill，对应"基座 + 基座"。
- 安全边界：低置信度/技术失败 → `inconclusive`，不伪造结果。

## 风险问题话术

如果评委问"你们的 Skill 训练出来的基座，效果到底怎么样？"：

不报"99% 准确率"这种数字。理由：真实考场还没有完整标注集，姿势、光线、机位、人体差异都会影响数字。我们能做的是：(1) 给出训练集混淆矩阵；(2) 现场跑同一份数据让评委看；(3) 把置信度低的样本交给人工复核。技术失败返回 `inconclusive`，不会因为算错而冤枉候选人。

如果评委问"AI 会不会乱判未达标？"：

不会。三层防线：(1) 实时监测 / 实时纠错 / 实时计数三层分离；(2) `decision` 必须是 `pass / not_met / needs_retraining / inconclusive` 四种之一；(3) 最终录用由企业授权人员决定，系统只给结论，不替 HR 做决定。

如果评委问"基座 + 基座听起来很玄，能现场演示吗？"：

能。我们现在的 `model/` 目录就是"通用基座 + 垂直基座"两层落地的实物：ST-GCN 11 类微调权重是从 MM-Fit 通用基座上微调出来的；`data/demo/enterprise_demo.json` 就是给这家虚拟工厂"现场训练"垂直基座的请求样本。`docs/real-evidence.md` 列出了混淆矩阵和 GPU 推理日志，可以现场打开看。

如果评委问"基座训练要多少数据？会不会很贵？"：

微调 ST-GCN 11 类分类器不需要大规模数据：MM-Fit 21 受试者 + 仓库脱敏样本足以微调一个企业垂直基座。训练时长在 RTX 5070 Ti Laptop GPU 上约几十分钟到数小时（具体看样本量），不需要云端 API。垂直基座是企业私有资产，复用一次训练、长期使用，按企业招聘批次摊薄后成本很低。

如果评委问"实时监测和实时纠错，会不会因为延迟误导候选人？"：

Web 端到端的实时链路是 RTMPose 关键点（毫秒级）+ ST-GCN 48 帧窗口滑动（约 1.5 秒延迟）+ 规则引擎（毫秒级）。语音播报靠 Web Speech API 在规则引擎输出时立刻触发。延迟在体感上是"立刻"。如果候选人动作极快错过底部停留，规则引擎会标"幅度不到位"——这是纠错而不是误判。

如果评委问"Ollama 不装能不能跑？"：

能。Ollama 只是用于生成式教练文案（可选）。实时监测 / 实时纠错 / 实时计数 / 认证记录全部不依赖 Ollama。Ollama 不可用时，规则反馈继续工作，只有"AI 教练解释"那段降级显示 Gemma 错误提示。这是核心实时链路和 LLM 增强解耦的好处。

如果评委问"为什么是 ClawHive？"：

因为我们要服务的是企业 HR 和 EHS，不是个人健身用户。HR 已经在飞书/钉钉/企微/OA 里办公，HR 不愿意再开一个新后台。ClawHive 让我们的双 Skill（训练 Skill + 实时纠错 Skill）以 Skill 形式进入 HR 已有工作流：HR 发起训练请求 → 训练 Skill 产出垂直基座 → 部署后 HR 发起实时检测 → 实时纠错 Skill 在垂直基座上做实时反馈 → 结果回写到招聘台账。这是企业级 AI 应用最自然的形态。

如果评委问"投资人应该关注什么？"：

关注三件事：(1) 垂直基座作为可复用企业资产的网络效应——每多一家企业，多一个专属基座；(2) 实时纠错应用层的标准化与可审计能力；(3) 嵌入 ClawHive 权限和业务系统的连接资产。视觉模型是开源的，壁垒在企业专属垂直基座 + 实时纠错应用层 + ClawHive 编排。
