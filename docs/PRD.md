# PRD：Enterprise Pose Coach · 安姿盾

- 文档版本：v1.0
- 更新时间：2026-08-07
- 比赛方向：AI-开发为主，AI-视听为核心能力
- 产品阶段：黑客松 MVP
- 主交付载体：可被 ClawHive 编排的企业级视觉 Skill

## 0. 产品判断与参赛亮点

项目现有的强项是真实的本地视觉模型、实时动作规则、固定 50 次认证和完整 Web 交互，这与制造企业招聘/转岗中的批量体能检测天然匹配。单纯讲“AI 健身”商业付费方不清楚；只讲招聘计数又容易被视为单点工具，且会被追问误判、申诉和劳动合规。

因此采用“先切招聘、再做在岗”的双阶段路线：第一阶段以招聘/转岗体能检测为付费切入口，AI 自动计数、判定动作有效性并输出达标证据，HR 对未达标或低置信度结果人工复核；第二阶段把同一套视觉、规则、任务和审计资产扩展为企业一线岗位动作合规与工效风险训练数字员工。ClawHive 负责批量发起、权限、通知、知识和回写，本项目负责看动作、纠错和给出结构化结果。

参赛差异化：

1. **真模型**：已有 RTMPose、ST-GCN 权重、11 类真实数据训练结果，不是纯大模型对话或视频生成。
2. **真闭环**：任务发起 → 摄像头采集 → 实时纠错 → 达标/复训 → 结构化报告 → 审计记录。
3. **切入口刚需**：招聘高峰的人工计数成本随候选人数线性增长，自动计数和留痕价值直观可演示。
4. **企业可控**：原始视频默认本地处理；Skill 只回传必要的结构化事件，便于最小权限、数据留存和审计。
5. **可扩张资产**：招聘体能标准和老师傅/EHS 动作标准都能转成版本化规则，入职后继续用于在岗复训。
6. **边界清楚**：系统做岗位相关项目的达标筛选，低置信度转人工；最终录用、处分和医疗决定不由模型独立作出。

## 1. 项目一句话描述

> 安姿盾是嵌入 ClawHive 的企业体能与岗位动作评估数字员工，用普通摄像头先完成招聘/转岗体能自动计数、达标筛选与证据留痕，再延伸到在岗动作合规和工效风险训练。

## 2. 目标用户

| 用户 | 直接目标 | 使用方式 |
|---|---|---|
| 招聘负责人/HR（第一付费方） | 在招聘高峰低成本完成岗位相关体能初筛 | 创建批次标准、查看结果、人工复核争议项 |
| EHS/安全负责人（共同规则 Owner） | 确保测试项目与岗位需求相关，并降低在岗培训执行偏差 | 配置体能/岗位标准、抽样复核、查看高频问题 |
| 招聘考官/班组长 | 不再逐人肉眼计数，快速处理异常 | 在飞书/钉钉/企微发起、催办、查看需复核项 |
| 候选人/转岗员工 | 清楚知道哪些动作被计为有效，并获得公平复核机会 | 摄像头完成检测，获得实时提示和结果 |
| 在岗一线员工 | 入职后继续接受动作合规与工效风险复训 | 手机或工位摄像头训练，获得短句与语音反馈 |
| IT/合规管理员 | 控制数据、权限、模型和审计 | 配置租户权限、留存策略、私有化推理与审计 |

首个 ICP：招聘具有明确、岗位相关体能项目（如深蹲、俯卧撑、仰卧起坐），在旺季需要批量检测的一线制造、仓储或服务企业。切入购买方是招聘负责人，EHS/用工合规和 IT 为共同决策方；Land-and-expand 目标是在岗安全培训与工效风险管理预算。

## 3. 用户痛点

| 痛点 | 真实表现 | 可验证的业务指标 |
|---|---|---|
| 招聘高峰人工计数成本高 | 考官逐个盯住候选人计数并判断动作是否有效，吞吐量受人力限制 | 单人检测时长、每百人考官工时、并行检测人数 |
| 筛选标准不一致且易争议 | 不同考官对动作幅度、起止状态和漏数判断不同 | 人工复核率、改判率、候选人申诉率 |
| 招聘结果缺少过程证据 | 纸面只记录最终次数，事后难解释“哪一次为什么没算” | 有效动作事件覆盖率、争议处理时长 |
| 培训“看过不等于会做” | 视频课程和签到只能证明参加，无法证明动作掌握 | 首次达标率、复训后达标率 |
| 人工一对一观察无法规模化 | 老师傅或安全员在培训高峰被重复占用 | 单人考核时长、每批人工工时 |
| 标准依赖个人经验 | 不同教练对幅度和危险姿势判断不一致，争议难复核 | 复核改判率、规则一致性 |
| 结果没有结构化沉淀 | 纸质签到和口头结论不能形成岗位风险画像 | 有效报告覆盖率、审计查询耗时 |
| 视频上云带来隐私压力 | 原始人像属于敏感数据，跨系统流转增加泄露面 | 原始视频上传比例、留存到期删除率 |
| AI 工具与企业流程割裂 | 单独 App 需要员工重新登录，结果无法回到 OA/IM | 任务触达率、按时完成率、回写成功率 |

MVP 验证招聘检测吞吐、计数一致性和可追溯性，并演示向在岗培训扩展。它不宣称“降低工伤率”这一长期因果结果，也不把体能单项达标等同于完整岗位胜任力。

## 4. Demo 场景

### 主 Demo：招聘高峰体能检测与筛选

背景：某工厂当天有 30 名一线岗位候选人，需要完成 50 次深蹲体能项目。过去由考官逐人计数并肉眼判断动作是否到位；现在希望 AI 并行计数、解释无效动作并保存达标结果。

1. 招聘负责人在 ClawHive 中说：“给今天的一线招聘批次创建深蹲 50 次体能检测，18:00 前完成。”
2. ClawHive 从企业知识库选择 `RECRUIT_SQUAT_50_V1`，检查操作权限，向候选人/考官发送检测链接。
3. 候选人阅读摄像头用途、数据留存和复核说明后开始；Demo 全程使用虚构身份。
4. RTMPose 提取关键点，规则引擎识别“下蹲→站立”完整周期；未达到动作幅度的次数不计入有效次数，并立即给出纠正提示。
5. 达到 50 次后生成认证记录；未达标或关键点置信度不足时标记为“未达标/需复核”，不静默淘汰。
6. ClawHive 把结果回写招聘台账并通知 HR。HR 查看结构化报告与必要证据，决定是否进入下一招聘环节。

### 扩展 Demo：入职后的安全搬运姿势复训

候选人入职后，同一套会话、规则、通知和审计能力加载 `SAFE_LIFT_V1`，帮助班组长发起“屈髋屈膝、躯干稳定”的安全搬运代理动作复训。当前深蹲规则只能作为可运行代理样例；在采集工业场景数据并由 EHS 校准前，不宣称已完成生产级工效风险识别。

### 3 个比赛 Sample

| Sample | 演示内容 | 当前可运行能力 | 48 小时补齐项 |
|---|---|---|---|
| S1 招聘深蹲检测 | 50 次深蹲自动计数、无效动作纠正、达标记录 | `/coach`、姿态规则、`/certification` | 招聘批次与 Skill 输出适配 |
| S2 多项目体能筛选 | 俯卧撑/仰卧起坐等项目识别与结构化汇总 | 11 类动作识别、6 类专项规则 | 每项目目标次数配置与组合判定 |

## 6. 明确不做什么

1. 不让模型独立作出最终录用、辞退、绩效处分或薪酬决策；MVP 只按企业预设、与岗位相关的项目输出达标筛选结果，并保留人工复核。
2. 不做疾病诊断、康复处方、伤病预测或替代医生/职业健康专家。
3. 不把单摄像头模型当作生产现场的强制安全联锁，不控制机器启停。
4. 48 小时内不做多人同屏跟踪、跨摄像头追踪、人脸识别和身份核验。
5. 不在 48 小时内重训大型视觉模型；优先复用现有权重与规则并完成可验证闭环。
6. 不同时扩建 Flask、FastAPI 和 React Native 三条主链路；比赛主链路只用 Flask Web。
7. 不默认长期保存原始视频，不把人像上传到大模型；只保留达成业务目标所需的最少结构化数据。
8. 不承诺未经试点验证的“工伤下降 70%”等效果数字。
9. 不做复杂计费、商城、社交排行或区块链存证；这些不是首个企业成交的关键阻塞点。

## 7. 数据模型

### 7.1 核心实体

| 实体 | 关键字段 | 说明与留存建议 |
|---|---|---|
| `Tenant` | `tenant_id`, `name`, `retention_policy`, `timezone` | 企业租户与数据策略 |
| `Actor` | `actor_id`, `tenant_id`, `role`, `external_user_id` | 候选人/员工/考官/主管；MVP 不采集身份证号 |
| `PostureStandard` | `standard_id`, `scenario_type`, `name`, `exercise`, `target_reps`, `thresholds`, `rule_version`, `status` | 招聘体能或在岗训练标准，必须岗位相关且版本化 |
| `AssessmentTask` | `task_id`, `tenant_id`, `purpose`, `standard_id`, `assignee_id`, `batch_id`, `due_at`, `created_by`, `status` | ClawHive 发起的招聘、转岗、训练或复训任务 |
| `AssessmentSession` | `session_id`, `task_id`, `started_at`, `ended_at`, `device_type`, `model_version`, `consent_version` | 一次实际检测/训练会话 |
| `Observation` | `timestamp_ms`, `phase`, `confidence`, `errors[]` | 高频帧结果；MVP 可只在内存保留并聚合 |
| `RiskEvent` | `event_id`, `session_id`, `code`, `severity`, `first_seen_ms`, `duration_ms`, `cue` | 去抖后的有效问题事件 |
| `SessionReport` | `report_id`, `session_id`, `valid_rep_count`, `invalid_rep_count`, `score`, `decision`, `top_errors[]`, `review_status` | `decision`: `pass/not_met/needs_retraining/inconclusive` |
| `EvidenceRef` | `evidence_id`, `session_id`, `kind`, `uri`, `sha256`, `expires_at` | 默认不创建原视频；需要时受权限和留存控制 |
| `AuditEvent` | `audit_id`, `tenant_id`, `actor_id`, `action`, `resource_type`, `resource_id`, `occurred_at`, `request_id` | 只追加、不存密钥和原始图像 |

### 7.2 关系

```text
Tenant 1──N Actor
Tenant 1──N PostureStandard 1──N AssessmentTask
Actor 1──N AssessmentTask 1──N AssessmentSession 1──1 SessionReport
AssessmentSession 1──N RiskEvent
AssessmentSession 0──N EvidenceRef
Tenant 1──N AuditEvent
```

### 7.3 最小化原则

- 原始帧默认只在端侧/本地推理进程中存在，不进入 LLM 上下文。
- 结构化报告默认保存 180 天只是建议值，最终由企业策略配置；Demo 不硬编码法规期限。
- `assignee_id` 使用企业内部或批次内临时标识，Demo 使用完全虚构数据。
- 模型置信度不足或关键点缺失时返回 `inconclusive`，不把技术失败当作体能未达标。

## 12. 最大技术风险和备选方案

### 最大风险：高影响筛选中的误计数与泛化

招聘筛选会直接影响候选人机会。现有模型主要来自健身动作数据，不同体型、服装、相机角度、遮挡和动作节奏都可能造成漏计或误计。如果产品只给一个不可解释的 `fail`，即使平均准确率不错，也会在争议、合规和企业采购中失去信任。第二阶段的安全搬运还存在箱体遮挡、负重和工装等额外领域错配。

控制方案：

1. 只采用企业已在执行、与岗位直接相关且经 HR/EHS/法务确认的体能项目；系统不自行发明筛选标准。
2. 每个有效/无效动作保留时间点和规则原因；候选人可当场重试，低置信度、遮挡或多人场景输出 `inconclusive` 并转人工。
3. 在目标人群和固定考场条件下做计数一致性测试，重点记录误拒率与人工改判率，而不是只报总体准确率。
4. 现场固定机位、光线和距离，先做 3 秒入镜校准；真实模型失败时由人工接管，不用 seed 数据形成真实招聘结果。
5. 第二阶段的 `SAFE_LIFT_V1` 在工业数据与 EHS 校准完成前只作为代理训练 Demo。

### 备选方案

| 风险触发 | 主方案 | 备选方案 | Demo 话术 |
|---|---|---|---|
| GPU/模型加载失败 | 本地 RTMPose + ST-GCN | `npm run demo` 的确定性姿态 seed | “同一 API 与规则闭环，视觉依赖已降级” |
| 摄像头权限失败 | 浏览器实时帧 | 预录视频或 seed 数据 | “企业环境可配置受控采集终端” |
| ClawHive 接口变更/未拿到凭证 | 真实 Skill/Webhook | 固定契约 + Mock callback + 录屏 | 明确标注 Mock，不伪装真实调用 |
| 招聘现场模型不稳定 | 固定考场 + 模型计数 | 人工计数接管并保留技术失败原因 | “技术失败不等于候选人未达标” |
| 工业数据不足 | 专家规则 + 小样本校准 | 第二阶段只展示代理训练，不做现场监控 | “先招聘计数落地，再逐步扩大岗位场景” |
| 原始视频合规受阻 | 本地推理，仅传结构化事件 | 完全不保存视频，争议由现场重测 | “默认数据最小化” |
| 生成式模型不可用 | ClawHive/本地 LLM 生成解释 | 固定安全文案库 | “核心判断是确定性规则，不依赖大模型” |

## 附：商业化与投资叙事

首个可售产品不是“万能 AI 教练”，而是“一个招聘批次、一个体能标准、一个筛选闭环”的试点包。建议先在一个考场并行运行 AI 与人工计数，比较每百人考官工时、计数一致性、需复核率和争议处理时长；验证后按检测次数或私有化年费收费。随后把已部署的摄像头、账号、通知和规则平台扩展到在岗复训，形成 land-and-expand。定价必须在得到首批访谈和人工成本基线后确定。

长期壁垒来自四类资产的组合：经验证的招聘/岗位标准、真实场景的脱敏关键点与错误事件数据、可解释的人工复核闭环，以及深度嵌入 ClawHive 权限与业务流程的连接能力。模型本身不是唯一壁垒，可信筛选、持续复训和企业知识资产才是。
